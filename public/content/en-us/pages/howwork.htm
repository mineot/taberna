How Taberna works

Taberna is a foundation for personal sites, portfolios, and landing pages. It brings together an application that organizes the site, content files you can edit, and resources to customize the presentation.

To work with the project, it helps to understand how these parts connect: where the texts live, how a page is loaded, how languages are chosen, and what needs to be generated to publish the site.

The project's logic

Taberna runs entirely in the browser. The Vue application builds the interface structure and loads the HTML files that make up the content. Navigation between pages is handled by Vue Router.

Content is kept separate from the application components. You can review a text or change a menu's links by editing its HTML fragments. Changes to the layout structure and interactive behaviors live in the Vue files.

The result can be hosted as static files. The project does not require a backend to display its pages and does not include a database or admin panel: editing happens in your repository's files.

File organization

This is a simplified view of the folders and files used day to day:

public/

        themes.htm

    en-us/

src/
  App.vue
  AppTemplate.vue
  router.ts
  templates/
    default.vue
  components/
  styles/
  style-customs.css
  1. public/content/: holds the content, separated into folders by language.
  2. home.htm: contains the body of that language's home page.
  3. pages/: organizes the fragments for the inner pages.
  4. complements/: holds the shared pieces, such as the brand, menus, and footer.
  5. public/config/languages.json: defines the available languages and their information.
  6. public/images/, public/icons/, and public/fonts/: store resources used by the site.
  7. src/templates/: contains the layouts that organize the interface regions.
  8. src/components/: contains the application components.
  9. src/styles/: holds the theme, font, utility, and global style definitions.
  10. src/style-customs.css: gathers custom content styles, such as those used in this documentation.

The pages/ and complements/ folders help organize the content. Files are loaded through the paths given in the links and in the application; placing them in these folders does not automatically create menu entries.

How a page is assembled

When the site opens, the application starts detecting the language and builds the shared page structure. The content components wait for the language to be defined before fetching their files.

Each part has a responsibility:

  1. 1
    App.vue brings together the application structure, the current route page, and the loading and error screens.
  2. 2
    The template defines where the header, main area, footer, and sidebar are located.
  3. 3
    AppTemplate.vue fills the template regions with the corresponding complements and components.
  4. 4
    The router determines which content should appear in the main area.
  5. 5
    The tbc-flux component fetches the fragment in the active language and inserts its HTML into the page.

For example, the brand shown in the header, footer, and sidebar comes from the same file, complements/brand.htm. Changing that fragment updates the content used in those three regions on the next load.

When you navigate through an internal link, the main area receives the content of the new route, keeping the site's shared structure.

How to write the content

The .htm files must contain HTML fragments: only the elements that will be shown in that part of the site. There is no need to repeat the structure of a complete HTML5 document.

Use headings to organize the topics, paragraphs to develop the ideas, and lists when there is a sequence or a set of items. Links and images can also be part of the fragments.

Published content is interpreted as HTML. Taberna does not convert Markdown automatically; if you use Markdown to prepare a draft, you need to convert it to HTML before the final version.

Fragments can use style classes and custom components registered by the project. Vue expressions and directives, such as interpolations and v-if, are not compiled in these files. Behaviors that depend on Vue must be implemented in the application components.

These files are author content owned by the site owner. The loader does not sanitize the HTML, so only publish content you know and have reviewed.

Pages and navigation

Internal links use the # format. The home page is at #/, and the language switcher is at #/language.

For content pages, the part after #/ indicates the fragment's path inside the active language folder. For example: 

Address: #/pages/howwork.htm
Active language: pt-br
File: public/content/pt-br/pages/howwork.htm

The same address, with English active, looks for public/content/en-us/pages/howwork.htm. The language does not need to appear in the link.

Adding a page

To create a page called About, follow this sequence:

  1. 1
    Create pages/about.htm inside the folder of every enabled language.
  2. 2
    Write the corresponding content in each language, keeping the same file name and path.
  3. 3
    Add the link in the navigation complements where you want to make the page available.
  4. 4
    Check access to the page and language switching in the local environment.

The link can be written like this:

 <a href="#/pages/about.htm">About</a>

The header menu and the sidebar menu have separate files: complements/header-nav.htm and complements/sidebar-nav.htm. Edit both when you want the page to appear in both navigations.

For this kind of page, the generic route already forwards the path to the loader; there is no need to register a Vue route for each fragment.

Paths and loading failures

Fragment paths must end in .htm. In the value forwarded to the loader, do not use a leading slash, backslashes, empty segments, or ... Subfolders are allowed, as in pages/about.htm.

If a file does not exist, cannot be loaded, or the hosting returns a complete HTML document instead of the fragment, the application shows its error screen. Currently, there is no specific content page for not found and no automatic fallback to the translation in another language.

How languages work

The file public/config/languages.json brings together four pieces of information:

  1. default: the default language.
  2. available: the list of enabled languages.
  3. flags: the flags associated with each language.
  4. names: the names shown in the switcher.

The current configuration is:

{
  "default": "en-us",
  "available": ["pt-br", "en-us"],
  "flags": { "pt-br": "🇧🇷", "en-us": "🇺🇸" },
  "names": {
    "pt-br": "Português (Brasil)",
    "en-us": "English (United States)"
  }
}

On startup, Taberna looks for an available language in this order:

  1. 1
    The preference saved in the browser from a previous visit.
  2. 2
    The language preferences reported by the browser.
  3. 3
    The default language from the configuration.
  4. 4
    The first available language, if the default is not in the list.

Use lowercase identifiers, such as pt-br and en-us, and keep those names in the content folders. Matching considers the complete identifier: a pt preference is not automatically converted to pt-br.

When you choose another language, the preference is saved in the browser's local storage and the page reloads, keeping the current page address. If the browser blocks writing that preference, the choice may not persist.

To enable another language, add its information to the configuration and prepare all the corresponding fragments, including pages and complements. Translations are written by you; there is no automatic translation. This organization by language applies to the content, while some interface messages are still hardcoded in English.

Customization: the role of each resource

Themes

The theme defines the shared visual identity: colors, fonts, spacing, borders, and other details. Its variables live in src/styles/theme.css and are used by the project's styles and utilities.

Changing these definitions lets you adjust the appearance of several regions consistently. To learn about the visual configuration, see the Themes page.

Templates

Templates define the layout structure. They organize regions such as the header, main content, footer, and sidebar and offer spaces, called slots, to receive content.

Currently, there is the src/templates/default.vue template. The src/AppTemplate.vue file imports that template and connects its slots to the application's complements and components.

Over time, various types of templates will be created for different site purposes. Feel free to create your own, adapting the structure to your project's needs.

Creating a template involves working on the Vue layout and integrating it into AppTemplate.vue; the application does not offer an automatic template selector. The templates page is the place to go deeper into this customization.

Components

Components bring together reusable features and behaviors. Among the elements available for content are tbc-flux, which loads fragments, tbc-language, which leads to the language switcher, and tbc-carousel, which arranges items in a carousel.

Each component has its own purpose and may offer configuration attributes. The components page covers the topic separately.

Utilities

Utilities are classes that apply visual rules directly to HTML elements. Taberna uses Tailwind CSS and its own classes with the tbu-* prefix, defined in src/styles/utilities.css.

They help apply the theme colors, spacing, borders, and other resources without repeating the same CSS rules in every content snippet. The details are on the utilities page.

From development to publishing

Prepare your copy

Have Git, Node.js 24, and npm installed. You can fork Taberna on your GitHub account to keep your customizations in your own repository.

To start from the original repository:

git clone https://github.com/mineot/taberna.git
cd taberna
npm install

If you created a fork, replace the command address with your repository's address.

Work locally

Start the development server:

npm run dev

Open the address shown in the terminal. Edit the content fragments and check the result in the browser. If needed, reload the page to fetch the changed files again.

A practical sequence is to customize the brand and the home page, prepare the inner pages, adjust the menus, and check the content in each language. After that, work on the theme and the other visual adjustments.

Generate and check the production version

When you want to prepare the site for publishing, run:

npm run build

This command checks TypeScript and generates the production files in dist/. The public files, including the content fragments, are copied to that output.

To check the result locally:

npm run preview

The preview is used to review the build before publishing it. Check the links, the images, the pages, and language switching; a successful build does not validate that all translations and all link destinations exist.

Publish the site

Send the contents of dist/ to the static hosting you chose. The upload process depends on the service used; the project does not include an automatic publishing workflow.

If you publish in a subdirectory, check the resource paths in the fragments. For example, /images/logo.png points to the domain root, while images/logo.png is relative to the base address of the displayed page. Paths are not resolved from the fragment's folder and are not rewritten automatically by the build.

Keep your changes in the source files, generate a new build, and publish the updated output. That way, your repository remains the reference for the site's content and customizations.
